# 失敗した LLM 呼び出しに、実際いくら課金されるのか

Amazon Bedrock は「どの失敗が課金対象か」を公開していません。そこで実際に測りました。
測定先は AWS 自身が出しているカウンターです。結果は、ほとんどのクライアントライブラリが
前提にしていることと食い違います。

この文書は Stratoclave を使うかどうかとは無関係に読めます。書いてあるのは Bedrock と
AWS SDK の挙動であって、このプロジェクトの仕様ではありません。各項目には証拠が切れる場所を
書き、5 件のうち 3 件は末尾のハーネスで再現できます。残り 2 件は、どこまでが自動化されて
いないかを明記しました。

LLM 呼び出しの利用量を数える、予算上限を設ける、あるいは再販する仕組みを作っているなら、
まずここを読んでください。要点は 1 つです。**「クライアントに何も返ってこなかった」ことは
「課金されていない」ことの証拠になりません。** これを前提にした予算管理は、自分では
把握できない支出を生みます。

## 5 つの測定結果

| よくある思い込み | 実際に測った結果 | 証拠が切れる場所 |
|---|---|---|
| エラーなら課金されない | クライアント側 2 秒の read timeout で**打ち切った** Converse 呼び出しに、**出力 1,493 トークン**が記録された。呼び出し側は何も受け取っていない | 1 試行、1 モデルファミリー。この SDK 側の read timeout がサービス側の実行を止めなかったことを示すだけで、あらゆるタイムアウトが同じとは言えません |
| 課金は HTTP ステータスに対応する | 境界は「**モデルが動いたか**」であって、呼び出しが失敗したかではない。サービス側の拒否 (`ValidationException`、HTTP 400) は呼び出しを 1 件記録するが、**トークンのカウンターは記録なし**。完走したストリームは正確な利用量を記録する | 測ったのは `ValidationException` だけです。他の拒否コードや HTTP ステータスは、**カウンターではなく論拠によって**同じ 0 を引き継いでいます |
| `Invocations` は課金の件数 | `Invocations` は**課金されない拒否も数える**。請求に最も近い指標はトークンのカウンター側 | これは件数なので、有償か無償かも金額も区別できません |
| `max_attempts: 1` なら 1 回だけ呼ぶ | botocore が `total_max_attempts = 2` として解決し、渡した dict をその場で書き換える | botocore 1.35.99 に対してオフラインで再現しています。**2 回目の課金**自体は同じアカウントで測りましたが、ハーネスが確認するのは解決結果までです |
| 打ち切った呼び出しは紐付けできない | model invocation logging を有効にしておくと、打ち切った呼び出しの記録が **`requestMetadata` のマーカーだけで**取り出せた。中身は `in 22 / out 1,493` | 観測できた記録は 2 件で、到着は呼び出しの 35 秒後と 41 秒後。**Converse だけ**です (OpenAI 互換エンドポイントではマーカーが `null` で記録される)。取り出しは手作業で、ハーネスはマーカーを付けるところまでです |

上記はすべて **2026-08-29、us-east-1** での測定です。1 分あたり 1 条件だけを実行し、
このアカウントが普段使っていないモデルを使い (他のトラフィックがカウンターに混ざらないように)、
クライアント側の推計ではなく CloudWatch の `AWS/Bedrock` メトリクスを読んでいます。
このメトリクスは請求書の明細ではなくプロバイダ側のテレメトリです。on-demand の料金は
トークン単位なので、「出力 1,493 トークンが課金された」は「呼び出し側が何も受け取らなかった
呼び出しについて、プロバイダが出力 1,493 トークンを記録した」という意味になります。

これは存在証明であって分布ではありません。「エラーは無料」を覆すには反例 1 件で足りるので
1 試行で決着しますが、発生率を語るには足りないので、この文書に発生率は一切書きません。

**ここで使った用語**を 1 回ずつ説明します。*Converse* は Bedrock 自身のリクエスト API です
(OpenAI 互換エンドポイントと対比されます)。*read timeout* は、まだ待っている応答を
クライアント側から諦めることです。*model invocation logging* は呼び出し 1 件ごとに記録を
S3 や CloudWatch Logs へ書く Bedrock の設定で、プロンプトと応答の本文を含めない設定もできます。
*`bedrock-mantle`* は古い OpenAI 互換の面で、Stratoclave はもう使っていません。
*CUR* は AWS Cost and Usage Report、つまり明細つきの請求データです。

## 測定 1: あなたのタイムアウトは、モデルのタイムアウトではない

クライアント側の read timeout は「どれだけ待つか」という自分のプロセスの判断です。
その判断はプロバイダには伝わりません。モデルは生成を続け、完走し、生成したトークンが課金されます。

測定条件は、Converse 呼び出し 1 回、SDK の試行 1 回、read timeout 2 秒、
モデルが長く答えたくなる入力です。

| 観測した指標 | 値 |
|---|---|
| 呼び出し側が受け取ったもの | なし (`ReadTimeoutError`) |
| `Invocations` | 1 |
| `OutputTokenCount` | **1,493** |
| model invocation logging の記録 | `in 22 / out 1,493` |

予算を預かる仕組みにとっての帰結は明確です。この失敗では予約を**返してはいけません**。
返すと、アカウントが実際に使ったお金を戻すことになり、次の入場がそれをもう一度使えてしまいます。
Stratoclave では、この判断は 1 つの表 (`backend/mvp/provider_outcome.py`。各行が測定結果を
根拠として引用しています) と、予約を終わらせられる唯一のオブジェクト
(`backend/mvp/_money.py`) にまとまっています。

## 測定 2: 境界は「モデルが動いたか」

失敗は 1 種類ではありません。5 つの条件を実行し、値段の違う 3 つの分類に分かれました。

| 条件 | `Invocations` | トークンのカウンター | 課金 |
|---|---|---|---|
| 自分側のシリアライザが拒否 (botocore の `ParamValidationError`) | 記録なし | 記録なし | されない (リクエストが出ていない) |
| サービスが拒否 (`ValidationException`、HTTP 400) | 1、加えて `InvocationClientErrors` 1 | **記録なし** | されない (モデルが動く前に拒否) |
| ストリームを消費側が 2 イベントで閉じた | 記録なし | **記録なし** | されない |
| read timeout で打ち切った | 1 | **出力 1,493** | **される** |
| ストリームが完走した | 1 | 正確な usage | される |

つまり問うべきなのは「例外が出たか」ではなく「**どこまで進んだか**」です。送られていないか、
推論の前に拒否されたか、送られたが完了を示す情報が返ってこなかったか。課金され得るのは
3 番目だけで、しかも 3 番目はネットワークエラーと見分けがつきません。

判別できなかったものは 3 番目に入れるべきです。この方向に間違えると、
テナントの予算枠を一時的に余分に押さえてしまいます。逆方向に間違えると、
予算上限そのものが破れます。この 2 つは対称ではないので、既定値も対称にしません。

## 測定 3: `Invocations` は課金の代理指標にならない

これは逆向きの罠です。`Invocations` は**課金されなかった**拒否を数えていました。
そして多くのコストダッシュボードが最初に手を伸ばすのがこのカウンターです。
これを読むと、拒否の嵐が支出のように見えます。トークンのカウンターを読めば、実態が見えます。

on-demand の料金はトークン単位なので、ほぼリアルタイムで見える中ではトークンのカウンターが
請求に最も近い指標です。なお、従来の CUR も CUR 2.0 もリクエスト単位の識別子を持たないため、
請求書レベルでのリクエスト単位の突合は、利用者にもゲートウェイにもできません。

## 測定 4: 予約 1 つで、プロバイダ呼び出しが複数回

`botocore.config.Config(retries={"max_attempts": N})` は「合計 N 回」を意味しません。
botocore が `total_max_attempts = N + 1` に書き換えます。実測はこうです。

| 指定 | botocore が解決した値 | 数えられた invocation |
|---|---|---|
| `retries={"max_attempts": 1}` | `total_max_attempts: 2` | **2** |
| `retries={"total_max_attempts": 1}` | `total_max_attempts: 1` | 1 |

さらに、渡した dict を**その場で書き換えます**。botocore 1.35.99 では、渡した
`{"max_attempts": 1}` がクライアント生成後に `{"total_max_attempts": 2, "mode": "legacy"}`
として読み出されます。つまり後から自分のリクエストを見ても、自分が何を指定したのか分かりません。

再試行が成功した場合、前の試行のトークンも課金されますが、コードから見えるのは**成功**です。
どこのエラー処理もその課金を観測しません。リクエスト単位で数えているなら、
SDK が黙って行った試行の分だけ数え落としています。

対策は 2 つです。`total_max_attempts` を明示すること。そして再試行の予算を、
SDK が解釈し直す設定キーではなく、自分で書いたルーターのループなど会計できる場所に置くことです。

## 測定 5: 打ち切った課金も、準備してあれば紐付けられる

呼び出しを打ち切った側は、プロバイダのリクエスト ID を知りません。しかも invocation ログの
`identity` はゲートウェイ自身のタスクロールで、どのテナントでも同一です。
つまり既定では、帰属先の分からない利用量と突き合わせる手がかりがありません。

1 つだけ残ります。Bedrock は `requestMetadata` を model invocation log の記録に反映します。
実測では、read timeout で打ち切った呼び出しの記録が**そのマーカーだけで**取り出せ、
正確なトークン数を持っていました。

| 性質 | 実測値 |
|---|---|
| 取り出しに使った鍵 | `requestMetadata` のマーカー (リクエスト ID 不要) |
| 記録の中身 | `in 22 / out 1,493` |
| ログ配信先に届くまでの遅れ | 35 秒と 41 秒 (記録 2 件) |
| 本文の配信 | 無効 (記録はメタデータのみ) |

限界もそのまま書きます。これは **Converse だけ**です。OpenAI 互換エンドポイントでは記録自体は
存在しますが `requestMetadata` が `null` として記録されるため、リクエスト単位の帰属ではなく
集計としての証拠になります。`bedrock-mantle` では記録が一切作られません。
Stratoclave が OpenAI 互換のトラフィックを AWS 推奨のエンドポイントへ移した理由の 1 つがこれです。

マーカーは送信**前**にリクエストへ載せておく必要があるので、これを刻むことは最適化ではなく
正しさの要件です。載せる値はゲートウェイが自分で発行した ID だけで、
プロンプト、利用者の識別子、リクエスト内容から導いたものは含めません。

## 補足: テスト環境についての測定 2 つ

どちらも Bedrock の話ではありませんが、どちらも調査に何日も費やす原因になります。

| 測定結果 | 実測値 |
|---|---|
| 代用ストアを使うと、ローカルの計測は「多めに出る」のではなく**意味を失う** | 同じ呼び出しで `reserve_ms=13.7` (DynamoDB Local。実エンジンのローカル版) 対 `reserve_ms=9485.2` (moto。Python プロセス内のモック)。reserve だけで約 **690 倍** |
| ゲートウェイのリクエストで台帳は主要コストではない | `reserve_ms=13.7` + `settle_ms=13.3` に対して `upstream_ms=1217.2`。1.26 秒のリクエスト中、記帳は 27 ミリ秒 |

モックしたデータストアを相手にゲートウェイをベンチマークしているなら、
測っているのはモックです。

## 再現方法

`scripts/local/measure_provider_outcome.py` が 5 つの条件を実装し、プロバイダ自身の
カウンターを読み戻します (測定 1 から 3 に対応)。測定 4 の再試行設定の解決はオフラインで
確認します。測定 5 については、マーカーを付けるところまでが自動で、記録の取り出しは
自分のログ配信先に対する手作業です。Bedrock を呼べて CloudWatch を読める権限が必要で、実際にお金がかかり
(数セント程度)、各条件がカウンターの 1 分を独占するように**意図的に 1 分あたり 1 条件**しか
実行しません。

```bash
python3 scripts/local/measure_provider_outcome.py --region us-east-1 \
  --model us.anthropic.claude-haiku-4-5-20251001-v1:0 \
  --out /tmp/provider-outcome.json
```

アカウントが普段呼んでいないモデルを指定してください。そうでないと、
他のトラフィックがカウンターに混ざります。スクリプトは上の表を自分の測定値で出力し、
生のカウンター読み出しも併せて残します。カウンターの当該 1 分が空で返ってきた条件は、
測っていない 0 を報告するのではなく「データなし」として扱います。

再試行の測定はアカウント不要です。

```bash
python3 scripts/local/measure_provider_outcome.py --retry-arithmetic-only
```

## このリポジトリでの使われ方

- `backend/mvp/provider_outcome.py` — 状態 (観測) と liability policy (判断)。
  測定結果 1 つにつき 1 行で、各行が根拠の測定と、受け入れているリスクを明記しています。
- `backend/mvp/_money.py` — hold。予約を終わらせられる唯一のオブジェクトなので、
  すべてのルートが上の policy に問い合わせ、ルートが自分で答えることはできません。
- `docs/EVIDENCE.md` — 証拠の全体図。**検証できていないもの**も含みます。
- `backend/tests/test_provider_outcome_formal.py`、
  `backend/tests/test_money_lifecycle_discipline.py` — 性質の検証と、
  将来のルートが課金済みの呼び出しを黙って返金しないようにする静的チェック。
